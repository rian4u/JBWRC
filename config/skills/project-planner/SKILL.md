# Vibe Coding Planner


Claude Code로 바이브코딩 프로젝트를 시작하기 전, 리서치부터 개발 지시서까지 4단계를 체계적으로 문서화하고 단일 CLAUDE.md를 생성하는 스킬.
---
## 전체 흐름

```
1단계: 리서치    → 01_research.md 저장  → 사용자 확인
2단계: 기획      → 02_planning.md 저장  → 사용자 확인
3단계: 설계      → 03_design.md 저장    → 사용자 확인
4단계: 개발지시서 → CLAUDE.md 최종 통합 생성
```

각 단계는 **반드시 사용자의 확인/승인을 받은 뒤** 다음 단계로 진행한다.
사용자가 수정을 요청하면 해당 단계 파일을 업데이트하고 다시 확인을 요청한다.

---

## 시작: 프로젝트 파악

스킬 시작 시 프로젝트 아이디어가 불명확하면 다음을 질문한다:

1. **무엇을 만들고 싶은가?** (한 줄 설명)
2. **주요 사용자는 누구인가?**
3. **핵심 기능 1~3가지는?**
4. **기술 제약/선호사항이 있는가?** (프레임워크, 언어, 플랫폼 등)

충분한 맥락이 있으면 바로 1단계로 진입한다.

---

## 1단계: 리서치 (Research)

### 목적

프로젝트의 시장성, 기술 가능성, 참고할 레퍼런스를 파악한다.

### 수행 내용

웹 검색을 적극 활용하여 다음을 조사한다:

* **시장/트렌드 조사** : 유사 서비스, 경쟁사, 시장 규모
* **기술 스택 조사** : 적합한 언어/프레임워크/라이브러리, 장단점 비교
* **유사 사례 분석** : 성공/실패 사례, 참고할 UX 패턴
* **기술적 리스크** : 구현 난이도, 잠재적 병목 지점
* **외부 API/서비스 조사** : 직접 구현 vs 외부 서비스 활용 검토

### 저장 형식: `01_research.md`

```markdown
# 리서치 보고서: [프로젝트명]

## 시장 현황
- 유사 서비스: ...
- 차별점 기회: ...

## 기술 스택 후보
| 영역 | 옵션 | 추천 | 이유 |
|------|------|------|------|
| 프론트엔드 | React / Vue / Next.js | Next.js | ... |
| 백엔드 | Express / FastAPI / ... | ... | ... |
| DB | PostgreSQL / SQLite / ... | ... | ... |

## 참고 레퍼런스
- [서비스명](URL): 참고할 포인트

## 기술적 리스크
- 리스크 1: 설명 / 대응 방안: ...

## 외부 서비스 활용 검토
- 직접 구현보다 외부 서비스가 유리한 기능: ...

## 리서치 결론
추천 기술 스택과 접근 방향 요약
```

### 단계 완료 후

> "리서치 결과입니다. 수정/추가할 내용이 있으신가요? 없으시면 기획 단계로 넘어가겠습니다."

## 2단계: 기획 (Planning)

### 목적

무엇을 만들지 명확히 정의한다. 범위를 확정하고 우선순위를 정한다.

### 수행 내용

* **프로젝트 개요** : 한 줄 정의, 핵심 가치 제안
* **타겟 사용자** : 페르소나 1~2개
* **기능 목록** : MVP vs 추후 기능 분리 (처음부터 너무 많은 기능은 지양)
* **유저 스토리** : 핵심 시나리오 3~5개
* **성공 지표** : 완성됐다고 볼 수 있는 기준
* **MCP 서버 검토** : 기능 구현에 필요한 외부 연동 파악
* **Claude Code 스킬 검토** : 활용 가능한 기존 스킬 파악

### MCP 서버 검토 가이드

기능 목록을 보고 각 기능이 외부 서비스 연동을 필요로 하는지 판단한다.

**자주 쓰이는 MCP 서버 예시:**

| 필요 기능               | 추천 MCP                               |
| ----------------------- | -------------------------------------- |
| Gmail/캘린더 읽기·쓰기 | `@google/gmail`,`@google/calendar` |
| GitHub 이슈·PR 관리    | `@github/github`                     |
| Slack 메시지 전송       | `@slack/slack`                       |
| 파일시스템 접근         | `@modelcontextprotocol/filesystem`   |
| 웹 브라우징/스크래핑    | `@modelcontextprotocol/puppeteer`    |
| DB 직접 쿼리            | `@modelcontextprotocol/sqlite`등     |
| Notion 읽기·쓰기       | `@notionhq/notion`                   |
| JIRA/Linear 티켓 관리   | `@atlassian/jira`등                  |

**판단 기준:**

* 외부 서비스 API를 직접 호출해야 하는가? → MCP 검토
* Claude Code가 파일 외 시스템 리소스에 접근해야 하는가? → MCP 검토
* 단순 코드 생성/편집만으로 충분한가? → MCP 불필요

### Claude Code 스킬 검토 가이드

* 문서 생성 (docx, pdf, pptx, xlsx) → 전용 스킬 존재 가능
* 특정 프레임워크 보일러플레이트 → 스킬로 표준화 가능
* 반복되는 도메인 지식 → `.claude/skills/`에 SKILL.md로 작성 권장

### 저장 형식: `02_planning.md`

```markdown
# 기획서: [프로젝트명]

## 프로젝트 개요
- **한 줄 설명**: ...
- **핵심 가치**: ...
- **타겟 사용자**: ...

## 기능 목록

### MVP (v1.0 - 핵심 기능만)
- [ ] 기능 1: 설명
- [ ] 기능 2: 설명

### 추후 버전 (v2.0+)
- [ ] 기능 A
- [ ] 기능 B

## 유저 스토리
1. 사용자는 [행동]을 통해 [목적]을 달성할 수 있다.
2. ...

## MCP 서버 검토
| 기능 | MCP 서버 | 필요 여부 | 비고 |
|------|----------|-----------|------|
| 이메일 발송 | @google/gmail | ✅ 필요 | OAuth 설정 필요 |
| 파일 읽기 | 없음 (코드로 처리) | ❌ 불필요 | |

## Claude Code 스킬 검토
| 작업 | 스킬 | 활용 여부 |
|------|------|-----------|
| 문서 생성 | docx skill | ✅ 활용 |
| 커스텀 스킬 | .claude/skills/my-skill.md | 개발 필요 |

## 성공 기준
- [ ] 기준 1
- [ ] 기준 2
```

## 3단계: 설계 (Design)

### 목적

기술적으로 어떻게 만들지 구체화한다. Claude Code가 바로 코딩할 수 있는 수준으로 상세화.

### 수행 내용

* **시스템 아키텍처** : 전체 구조, 컴포넌트 관계
* **기술 스택 확정** : 1단계 리서치 기반으로 최종 선택
* **폴더/파일 구조** : 프로젝트 디렉토리 트리 (`.claude/` 폴더 포함)
* **데이터 모델** : 주요 엔티티, DB 스키마 (해당 시)
* **API 설계** : 주요 엔드포인트 (해당 시)
* **화면 구성** : 주요 페이지/컴포넌트 목록 (UI 프로젝트의 경우)
* **환경 변수** : 필요한 설정값 목록
* **서브에이전트 전략** : Claude Code가 병렬 처리할 작업 설계
* **Hooks 설계** : 자동화할 품질 관리 작업 정의
* **코딩 컨벤션** : Claude Code가 지켜야 할 규칙 (구체적일수록 좋음)

### 서브에이전트 전략 가이드

Claude Code는 `Task` 도구로 서브에이전트를 병렬 실행할 수 있다.

**병렬 처리에 적합한 작업:**

* 서로 의존성이 없는 독립 모듈 (예: 컴포넌트 A, B, C 동시 구현)
* 백엔드 + 프론트엔드 동시 작업
* 여러 파일에 걸친 반복 작업 (타입 정의, 테스트 코드 일괄 생성)
* 독립적인 API 엔드포인트 구현

**순차 처리가 필요한 작업:**

* DB 스키마 확정 → ORM 모델 → API 구현 (의존성 있음)
* 인증 시스템 → 인증이 필요한 기능
* 공통 유틸/타입 정의 → 이를 사용하는 모듈

### Hooks 설계 가이드

Hooks는 CLAUDE.md 지시와 달리 **반드시 실행되는 자동화**다. 품질 관리에 특히 유용하다.

**자주 쓰이는 Hook 패턴:**

| 시점        | 용도                      | 예시                        |
| ----------- | ------------------------- | --------------------------- |
| PostToolUse | 파일 수정 후 자동 린트    | eslint, prettier 실행       |
| PreToolUse  | git commit 전 테스트 강제 | 테스트 미통과 시 커밋 차단  |
| Stop        | 작업 완료 시 알림         | 데스크탑 알림, Slack 메시지 |
| PostToolUse | 타입 체크 자동 실행       | tsc --noEmit                |

 **주의** : 린트 같은 단순 작업에만 적용. 과도한 Hooks는 컨텍스트 토큰을 낭비함.

### 저장 형식: `03_design.md`

```markdown

- **DB**: ...
- **배포**: ...

## 시스템 아키텍처
[텍스트 다이어그램 또는 설명]

## 4단계: CLAUDE.md 생성 (개발 지시서)

### 목적
앞선 3단계 문서를 통합하여, Claude Code가 즉시 개발에 착수할 수 있는 단일 마스터 문서 생성.

### CLAUDE.md 작성 원칙 (실전 베스트 프랙티스)

**반드시 지킬 것:**
1. **200줄 이하로 유지** — 길수록 Claude가 지시를 무시하는 경향이 생김. 자주 쓰이지 않는 정보는 `@docs/파일명.md`로 분리
2. **구체적인 예시 포함** — "100단어 설명보다 예시 파일 1개가 낫다". 코드 스타일은 실제 파일 경로로 참조
3. **IMPORTANT / MUST 강조** — 반드시 지켜야 할 규칙에만 대문자 강조 (남발하면 효과 없음)
4. **완전한 코드 명시** — `NEVER use placeholders`, `ALWAYS write complete code` 명시 필수
5. **개발 명령어 포함** — `npm run dev`, `npm test` 등 명시하면 Claude가 스스로 실행/검증함
6. **git 커밋 전략 포함** — 자주 커밋하도록 지시해야 엉뚱한 방향으로 달려가도 롤백 가능
7. **컨텍스트 관리 지침 포함** — 바이브코딩의 주요 실패 원인은 컨텍스트 오염. 관리 방법 명시
8. **git에 커밋** — 팀 전체가 공유하고 시간이 지나도 가치가 축적되도록 버전 관리

## 중요 원칙

- **웹 검색 적극 활용**: 리서치 단계에서 최신 기술 트렌드, 유사 서비스, 라이브러리 비교에 검색 도구 사용
- **구체성 우선**: 모호한 내용은 사용자에게 질문. Claude는 맥락 없이는 방향을 잃음
- **MVP 집중**: 기능을 과도하게 넣으면 스파게티 코드가 됨. 핵심 기능만 먼저
- **CLAUDE.md는 200줄 이하**: 길수록 Claude가 지시를 무시함. 자주 쓰이지 않는 정보는 @import로 분리
- **파일 저장 필수**: 각 단계 완료 시 반드시 파일로 저장하고 사용자에게 확인받음
- **완전한 코드 명시**: placeholder 금지, 완전한 코드 작성을 CLAUDE.md에 명시
- **컨텍스트 관리 포함**: 바이브코딩의 주요 실패 원인은 컨텍스트 오염. 관리 지침 반드시 포함
- **git 커밋 전략 포함**: 자주 커밋하도록 지시해야 엉뚱한 방향으로 달려가도 롤백 가능
