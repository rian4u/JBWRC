# plan-conventions.md — 기획서 작성 지침
> 로드 시점: 기획서 작성 시 및 필요 시마다
> 최종 수정일: 2026-03-24

---

## 기획서란 무엇인가

기획서는 **설계서를 작성하기 위해 필요한 모든 결정을 내리는 단계의 산출물**이다.
기획서가 완성되면 "무엇을, 왜, 어떤 도구로 만드는가"가 확정되고,
설계서에서는 "어떻게 구현하는가"만 남아야 한다.

기획서는 순서가 있는 프로세스가 아니라 **아래 관심사들이 모두 해소된 상태**를 의미한다.
어떤 관심사를 먼저 다루든 상관없다. 모든 관심사가 충족되면 기획이 완료된다.

### 관심사 목록

| 관심사 | 핵심 질문 | 섹션 |
|--------|---------|------|
| 목적과 범위 | 무엇을, 왜 하는가? | A |
| 정보 수집 | 모르는 것을 어떻게 알아내는가? | B |
| 외부 조사 | 다른 곳에서는 어떻게 하는가? | C |
| 기능 정의 | 구체적으로 무엇을 만드는가? | D |
| 보완 | 놓친 것은 없는가? | E |
| 산출물 | 기획서는 어떤 형태인가? | F |
| 유지보수 | 기획서가 바뀌면 어떻게 하는가? | G |

### 관심사 간 의존 관계

관심사에 강제 순서는 없지만, 자연스러운 의존 관계는 존재한다.
의존하는 관심사의 정보가 부족하면 해당 관심사로 돌아간다.

```
A (목적·범위) ← 다른 모든 관심사의 판단 기준
B (정보 수집) ← 어떤 관심사에서든 정보가 부족하면 사용
C (외부 조사) ← D에서 원자 액션이 확정될 때마다 벤치마크 수행
D (기능 정의) ← A의 목적이 명확해야 분해 가능
E (보완)      ← D의 각 레벨에서 역제안 수행
F (산출물)    ← 모든 관심사의 결과를 기획서로 조립
G (유지보수)  ← 기획서 완성 후 변경 발생 시 적용
```

## 기획서 완성 조건

아래가 모두 충족되어야 기획이 완료된 것으로 본다.
하나라도 미충족이면 해당 관심사로 돌아간다.
**기획서 초안 완성 후 `Agent` 도구로 검토 에이전트를 실행하여 아래 항목을 검증한다.**

| # | 검토 항목 | 통과 기준 | 관련 관심사 |
|---|---------|---------|-----------|
| 1 | 목적·범위 | 배경·목적·성공 기준이 명확하고 In/Out-scope가 확정되었는가 | A |
| 2 | 분해 완전성 | 모든 기능이 원자 액션까지 분해되었는가 | D |
| 3 | Leaf Test | 모든 원자 액션이 단일 행위자·단일 결과물·단일 책임·구현 가능성을 충족하는가 | D |
| 4 | 원자 액션 명세 | 모든 원자 액션에 입력·출력·기술 후보·마일스톤이 기재되어 있는가 | D |
| 5 | 벤치마크 완비 | 모든 기술 후보가 실제 리서치를 거쳐 작성되었는가 | C |
| 6 | 역제안 완료 | 각 레벨에서 역제안이 수행되고 결과가 기록되었는가 | E |
| 7 | 요구사항 추적 | 모든 요구사항 번호가 최소 하나의 원자 액션과 연결되는가 | D |
| 8 | 실현 가능성 | 제약사항과 충돌하는 액션이 없는가 | D, A |
| 9 | 리스크 검토 | 간과된 리스크가 없는가 | E |
| 10 | 미확정 처리 | `[미확정]` 항목에 결정 시점이 명시되어 있는가. 결정 시점이 '설계 단계 전'인 항목은 기획 단계에서 반드시 해소. 그 외는 설계 단계로 이관 가능 | F |
| 11 | 사용자 승인 | `AskUserQuestion`으로 사용자가 기획서를 승인했는가 | — |

검토 통과 후 사용자 승인을 받는다.
**승인 거절 시**: 거절 사유를 확인하고, 해당 사유와 관련된 관심사로 돌아가 부분 재작성한다. 전체 재작성은 사용자가 명시적으로 요구한 경우에만 수행한다.
**승인 후** `design-conventions.md`를 로드하여 설계서 작성을 시작한다.

## A. 목적과 범위 — "무엇을, 왜 하는가?"

이 프로젝트가 존재하는 이유와 경계를 확정하는 관심사다.
여기가 불명확하면 이후 모든 판단이 흔들린다.

**확정해야 할 항목:**

| 항목 | 설명 | 불명확할 때 발생하는 문제 |
|------|------|----------------------|
| 배경 | 왜 이 작업이 필요한가 | 우선순위를 정할 수 없다 |
| 목적 | 이 작업으로 무엇이 달라지는가 | "완료"를 판단할 수 없다 |
| 대상 | 누가 사용하는가, 무엇에 적용하는가 | 요구사항을 도출할 수 없다 |
| 성공 기준 | 어떤 상태가 되면 완료인가 | 검증 기준을 세울 수 없다 |
| In-scope | 이 프로젝트가 포함하는 것 | 범위가 끝없이 넓어진다 |
| Out-of-scope | 이 프로젝트가 명시적으로 제외하는 것 | "이것도 해야 하나?" 논쟁이 반복된다 |

**모호할 때:**
추측하지 않는다. `AskUserQuestion`으로 사용자에게 확인한다.
두 가지 이상 해석이 가능하면 반드시 질문한다.

## B. 정보 수집 — "모르는 것을 어떻게 알아내는가?"

기획에 필요한 정보가 부족할 때 사용하는 수단과 원칙이다.
어떤 관심사를 다루든 정보가 부족하면 이 섹션의 방법을 사용한다.

### B-1. 질문 원칙

- 모든 선택형 질의는 **반드시 `AskUserQuestion` 도구**를 사용한다
  텍스트로 번호 목록을 나열하지 않는다.
- "기타(Other)" 옵션은 명시하지 않는다 — 도구가 자동 제공한다
- 한 번에 최대 4개까지 질문할 수 있다. 묶을 수 있으면 묶는다
- 답변에서 추가 질문이 생기면 이어서 질의한다
- "이 정보면 기획서의 모든 관심사를 충족할 수 있는가?" 를 자문한다
  → 불가하면 부족한 관심사를 특정하여 추가 질의한다

### B-2. 질문 카테고리

어떤 상황에서 어떤 질문이 필요한지 판단하는 기준표다.
모든 카테고리를 묻는 것이 아니라, 해당하는 것만 선별한다.

| 카테고리 | 이런 상황일 때 필요 | 질문 예시 |
|---------|-------------------|----------|
| 대상 구체화 | 목적이 포괄적이거나 대상이 불분명 | 어떤 문서·데이터·업무가 대상인지 |
| 현행 프로세스 | 자동화·개선 목적 | 현재 어떻게 작업하는지, 병목은 어디인지 |
| 규모·빈도 | 반복 업무이거나 볼륨이 불명확 | 건수, 주기, 평균 소요 시간 |
| 품질 기준 | 산출물이 있음 | 표준 양식 존재 여부, 검증 기준, 허용 오차 |
| 우선순위 | 기능이 여러 개 | 가장 시급한 것, 나중에 해도 되는 것 |
| 환경·제약 | 실행 환경이 불명확 | 사내망 제약, 외부 도구 사용 가능 여부, OS |
| 예외·경계 | 정상 흐름만 파악된 상태 | 데이터가 없거나 형식이 깨진 경우 대응 |
| 성공 기준 | "완료"의 정의가 모호 | 어떤 상태면 프로젝트가 성공인지 |
| 유지보수 주체 | 완성 후 운영이 필요 | 누가 운영하는지, 기술 수준은 어느 정도인지 |
| 데이터 민감도 | 개인정보·기밀 포함 가능성 | 접근 제한이 필요한지, 암호화 요구 여부 |

### B-3. 사용자 프로필 (반복 질문 방지용 캐시)

기본 환경 정보(OS, 선호 언어, 기술 수준)는 `~/.claude/docs/users/[name].md`에 캐시되어 있다.
관리 규칙은 `~/.claude/CLAUDE.md §2`를 참조한다.
프로젝트별 상세 정보(사내망 제약, 배포 환경 등)는 프로필이 아니라 B-2에서 질문한다.

## C. 외부 조사 — "다른 곳에서는 어떻게 하는가?"

기술 판단을 내 지식만으로 하지 않는다.
**리서치 없이 기술 선택지나 추천 도구를 작성하지 않는다.**

### C-1. 리서치 항목

| 조사 대상 | 방법 | 산출물 (템플릿 섹션) |
|---------|------|-------------------|
| 도메인 모범사례 | 유사 프로젝트의 구현 방식·주의사항·실패 사례 웹서치 | `기술 리서치 결과` ← C |
| 도구·라이브러리 후보 | 기능 실현에 필요한 선택지를 최소 2개 이상 식별 | `기술 선택지` ← C |
| 현재 환경 설치 여부 | `pip list`, `npm list`, `brew list` 등 | ✅ 설치됨 / ❌ 미설치 표시 |

### C-2. 벤치마크 (기술 후보 비교)

원자 액션이 확정될 때마다 수행한다.

1. **웹서치** — 해당 액션의 모범 구현 패턴·주의사항 조사
2. **후보 탐색** — 구현 가능한 도구를 최소 2개 이상 식별
3. **환경 확인** — 이미 설치되어 있는 것 식별
4. **비교표 작성** — 후보 간 장단점·비용·라이선스·호환성 비교

비교 항목: 성능, 유지보수 활성도, 학습 곡선, 라이선스, 유료 여부, 현재 환경 호환성

**기술 스택 선택지를 제시할 때는 장단점·비용·라이선스를 반드시 함께 표시한다.**
옵션만 나열하고 근거 없이 추천하지 않는다.

## D. 기능 정의 — "구체적으로 무엇을 만드는가?"

기획서의 핵심이다.
기능을 **"더 이상 쪼갤 수 없는 단일 액션(원자 액션)"** 수준까지 계층적으로 분해한다.

**왜 이렇게 하는가:**
원자 액션 수준까지 분해되어야 설계서에서 "어떻게 구현하는가"를 명확히 쓸 수 있다.
분해가 불완전하면 구현 중 방향이 흔들리고, 누락 기능이 뒤늦게 발견된다.

### D-1. 원자 액션 판별 기준 (Leaf Test)

아래 조건을 **모두** 만족해야 원자 액션으로 확정한다.
하나라도 만족하지 않으면 반드시 더 분해한다.

| 조건 | 판별 질문 | 예시 |
|------|---------|------|
| 단일 행위자 | 하나의 함수·모듈·서비스가 수행하는가? | "파일을 읽고 변환하고 저장한다" → ❌ 세 행위자 |
| 단일 결과물 | 결과물이 하나인가? | "로그도 남기고 DB에도 저장한다" → ❌ 두 결과물 |
| 단일 책임 | "그래서 이걸 어떻게 해?"가 더 이상 안 나오는가? | "데이터를 처리한다" → ❌ 아직 불명확 |
| 구현 가능성 | 하나의 함수 또는 하나의 커밋으로 구현 가능한가? | "CSV를 읽어 리스트로 반환" → ✅ |

### D-2. 계층 분해 루프

모든 노드가 Leaf Test를 통과할 때까지 반복한다.

```
① 상위 기능을 정의한다
② "이 기능을 실현하려면 어떤 하위 동작들이 필요한가?" 자문
③ 하위 동작 목록을 도출한다
④ 각 하위 동작에 Leaf Test를 적용한다
   ├ 통과 → 원자 액션 확정 → 벤치마크(C-2) + 역제안(E) 수행
   └ 미통과 → 해당 노드를 새 상위 기능으로 삼아 ②부터 반복
⑤ 모든 노드가 통과할 때까지 반복
```

**판단이 모호하거나 해석이 두 가지 이상이면 즉시 `AskUserQuestion`으로 확인한다.**

### D-3. 계층 표기 방식

```
대기능
├ 중기능 A
│  ├ 소기능 A-1
│  │  ├ [원자] 액션 A-1-a   입력: X / 출력: Y / 기술 후보: Z / M1
│  │  └ [원자] 액션 A-1-b   입력: X / 출력: Y / 기술 후보: Z / M1
│  └ 소기능 A-2
│     └ [원자] 액션 A-2-a   입력: X / 출력: Y / 기술 후보: Z / M2
└ 중기능 B
   └ [원자] 액션 B-1         입력: X / 출력: Y / 기술 후보: Z / M1
```

**원자 액션에 반드시 포함할 항목:**
- 액션 설명 — 동사 + 목적어 (예: "CSV 파일을 읽어 딕셔너리 리스트로 변환한다")
- 입력 — 무엇을 받는가 (형식 포함)
- 출력 — 무엇을 만드는가 (형식 포함)
- 기술 후보 — 벤치마크 결과 선택한 도구
- 마일스톤 번호 — M1 / M2 등

### D-4. 마일스톤 분할

원자 액션이 많거나(5개 이상) 리스크가 높을 경우 마일스톤 단위로 분할한다.

**분할 기준:**
- 이 단위만으로 독립적으로 검증 가능한가
- M1만 완료해도 부분적 가치를 제공하는가
- 마일스톤 간 의존성이 단방향으로 명확한가

각 마일스톤 완료 후 사용자 승인을 받고 다음으로 진행한다.

## E. 보완 — "놓친 것은 없는가?"

사용자가 언급하지 않았지만 놓쳤을 가능성이 있는 항목을 적극적으로 찾아내는 관심사다.
**이 관심사를 건너뛰는 것은 금지다.**

### E-1. 역제안

기능 분해의 **각 레벨마다** 아래를 검토하고 역제안한다.
사용자가 명시적으로 거절하거나 "없다"고 할 때까지 계속한다.

| 역제안 유형 | 판단 기준 | 예시 |
|-----------|---------|------|
| 빠진 하위 기능 | 이 기능을 완성하기 위해 언급 안 된 동작이 있는가? | 로그인에 "로그아웃"이 없는 경우 |
| 더 단순한 대안 | 적은 단계로 같은 결과를 낼 수 있는가? | 라이브러리 하나로 2개 액션 대체 가능 |
| 숨겨진 의존성 | 선행되어야 하는 다른 액션이 있는가? | 파일 저장 전 디렉토리 생성 필요 |
| 리스크 | 실패할 수 있는 지점이 있는가? | 외부 API 지연, 파일 권한 오류 |
| 불필요한 복잡성 | 목적 대비 과도한가? | 단순 출력인데 DB를 연동하려는 경우 |

역제안은 기획서 `역제안 목록` 섹션에 기재하고, `AskUserQuestion`으로 수용/거절을 확인한다.

## F. 산출물 — "기획서는 어떤 형태인가?"

### F-1. 문서 규칙

- **기획서는 프로젝트 폴더의 `docs/기획서.md`에 저장한다** — 다른 경로에 저장하지 않는다
- 모든 문서 상단에 `최종 수정일` 기재, 수정 시마다 갱신
- 비어있는 섹션은 `(미작성)` 으로 명시 — 공백으로 두지 않는다
- 확정되지 않은 내용은 `[미확정]` 태그 — 결정 시 태그 제거 후 진행내역.md에 기록
- 삭제·변경 이력은 문서 내에 기재하지 않는다 — `docs/decisions/`에 별도 관리
- 문서 초안은 저장 전에 반드시 `AskUserQuestion`으로 사용자 승인을 받는다

### F-2. 기획서 템플릿

각 섹션 옆의 `← X` 는 해당 내용을 채우는 관심사를 나타낸다.

```markdown
# 기획서 — [프로젝트명]
> 최종 수정일: YYYY-MM-DD

## 개요                                          ← A
- **배경 및 목적**: 왜 이 프로젝트를 하는가
- **기대 효과**: 완료 후 무엇이 달라지는가
- **성공 기준**: 이 상태가 되면 프로젝트가 완료된 것으로 본다

## 범위                                          ← A
- **포함 (In-scope)**:
- **제외 (Out-of-scope)**:

## 요구사항                                       ← A, B
### 기능 요구사항
| # | 요구사항 | 우선순위 |
|---|---------|--------|
| F-01 | ... | 높음/중간/낮음 |

### 비기능 요구사항
- 성능: (해당 시 기재, 없으면 (해당 없음))
- 보안: (해당 시 기재)
- 운영: (해당 시 기재)

## 기능 계층 분해                                  ← D
대기능
├ 중기능
│  └ [원자] 액션 — 입력: / 출력: / 기술 후보: / 마일스톤: M1
└ 중기능
   └ [원자] 액션 — 입력: / 출력: / 기술 후보: / 마일스톤: M1

## 마일스톤 (원자 액션 5개 이상 시 작성)             ← D
- M1 — [기능명]: 포함 원자 액션 목록
- M2 — [기능명]: 포함 원자 액션 목록 (M1 완료 후)

## 기술 선택지                                     ← C
### [선택이 필요한 항목명]
| 기준 | 옵션 A | 옵션 B |
|------|--------|--------|
| 설명 | ... | ... |
| 장점 | ... | ... |
| 단점 | ... | ... |
| 비용 | 무료/유료 | ... |
| 라이선스 | MIT | ... |
| 추천 | ✅ | — |

## 기술 리서치 결과                                 ← C
- 도메인 조사 요약
- 추천 도구 목록 (✅ 설치됨 / ❌ 미설치)
- 참고 레퍼런스

## 역제안 목록                                     ← E
| 레벨 | 유형 | 내용 | 근거 | 결과 |
|------|------|------|------|------|
| 중기능 A | 빠진 기능 | ... | ... | 수용/거절 |

## 입출력 정의                                     ← D
- 전체 입력: 형식, 출처
- 전체 출력: 형식, 전달 대상

## 제약사항                                        ← A, B
- 기술·환경·정책 제약 사항

## 리스크                                          ← E
| 리스크 | 발생 가능성 | 영향도 | 대응 방안 |
|--------|-----------|-------|---------|
| ... | 높/중/낮 | 높/중/낮 | ... |

## 미결정                                          ← F
- [미확정] 항목명: 내용 — 결정 필요 시점: OO 단계 전
```

## G. 유지보수 — "기획서가 바뀌면 어떻게 하는가?"

### G-1. 기획서 업데이트 규칙

기획서는 최초 작성 후에도 아래 상황이 발생하면 반드시 업데이트한다.
**구현 중 요구사항이 변경되면 코드 작업을 즉시 중단하고 기획서부터 수정한다.**

| 트리거 | 업데이트 대상 | 연동 문서 |
|--------|------------|---------|
| 요구사항 추가·변경·삭제 | 요구사항, 기능 계층 분해, 마일스톤 | `진행내역.md`에 [변경], `decisions/`에 이유 |
| 기술 선택 변경 | 기술 선택지, 해당 원자 액션 기술 후보 | `decisions/`에 변경 이유 |
| 범위 조정 | 범위 섹션, 기능 계층 분해 | `진행내역.md`에 [변경] |
| 리스크 발생·해소 | 리스크 섹션 | `진행내역.md`에 [결정] |
| 미확정 항목 확정 | 해당 섹션의 `[미확정]` 태그 제거 | `진행내역.md`에 [결정] |
| 완료된 마일스톤 변경 | 해당 마일스톤 + 의존하는 후속 마일스톤의 원자 액션 | `진행내역.md`에 [변경], 설계서 해당 액션 갱신 |

업데이트 후 `최종 수정일`을 반드시 갱신한다.

### G-2. 연동 문서 템플릿

#### 진행내역 (`docs/진행내역.md`)

