# 문서 작성 지침
> CLAUDE.md는 "언제·무엇을", 이 문서는 "어떻게"를 담당한다.

---

## 1. 공통 규칙

- 모든 선택형 질의는 `AskUserQuestion` 도구를 사용한다
- "기타(Other)"는 도구가 자동 제공하므로 옵션에 포함하지 않는다
- **기술 스택 선택지**를 제시할 때는 장단점·비용·라이선스를 함께 표시한다
- 문서 초안은 사용자에게 보여주고 `AskUserQuestion`으로 승인/수정 요청을 받은 뒤 저장한다
- 모든 문서 상단에 `최종 수정일` 기재
- 비어있는 섹션은 `(미작성)` 으로 명시, 공백으로 두지 않음
- 확정되지 않은 내용은 `[미확정]` 태그 표시
- 삭제·변경 이력은 문서 내 별도 기재하지 않고 `docs/decisions/`에 기록

## 2. 사용자 프로필 (`~/.claude/docs/users/[name].md`)

### 2-1. 프로필 작성 원칙

프로필에 고정 항목 목록은 없다. **프로젝트의 목적에 따라** 이 사람에 대해 얼마나 알아야 하는지를 스스로 판단하여 필요한 만큼 `AskUserQuestion`으로 질의한다.

**판단 기준:**
- 이 프로젝트를 진행하려면 이 사람의 어떤 배경을 알아야 하는가?
- 응답 수준·용어 선택·설명 깊이를 결정하려면 무엇을 알아야 하는가?
- 기술적 선택을 제안하려면 이 사람의 어떤 경험·환경을 알아야 하는가?

**예시 (목적에 따라 달라짐):**
- 재무 문서 자동화 → 다루는 문서 유형, 현행 작업 방식, 사용 도구, 코딩 경험 수준
- 웹 서비스 개발 → 기술 스택, 배포 환경, 팀 규모, 선호 아키텍처
- 데이터 분석 → 데이터 출처, 분석 도구, 통계 지식 수준, 산출물 형태

### 2-2. 진행 방식

1. 프로젝트 목적을 먼저 파악한다 (CLAUDE.md §2 참조)
2. 목적을 기준으로 "이 사람에 대해 알아야 할 것"을 도출한다
3. `AskUserQuestion`으로 질의 (한 번에 최대 4개)
4. 답변을 프로필 파일에 자유 형식으로 기록한다
5. 이후 세션에서 프로필을 읽고, 새 프로젝트 목적에 비추어 부족한 정보가 있으면 추가 질의 → 프로필 갱신
6. 이미 기재된 항목은 다시 묻지 않는다

## 3. 요구사항 구체화 (기획서 작성 전 필수)

목적 + 사용자 프로필을 결합하여 "기획서를 쓰려면 아직 모르는 것"을 식별한다.
**이 단계를 건너뛰고 기획서를 바로 작성하지 않는다.**
**기획서에 더 이상 빈칸이 없는 수준**까지 질문한다.

### 3-1. 질문 도출 기준

| 질문 카테고리 | 도출 조건 | 질문 예시 |
|--------------|----------|----------|
| 대상 구체화 | 목적이 포괄적일 때 | 어떤 문서/데이터/업무가 대상인지 |
| 현행 프로세스 | 자동화·개선 목적일 때 | 현재 어떻게 작업하는지, 어디서 병목인지 |
| 규모·빈도 | 반복 업무일 때 | 건수, 주기, 소요 시간 |
| 품질 기준 | 산출물이 있을 때 | 표준 양식·서식 존재 여부, 검증 기준 |
| 우선순위 | 기능이 여러 개일 때 | 가장 시급한 것, 나중에 해도 되는 것 |
| 환경·제약 | 실행 환경·보안이 불명확할 때 | 사내 시스템 제약, 외부 도구 사용 가능 여부 |
| 예외·경계 | 정상 흐름만 파악된 경우 | 데이터가 없거나 깨진 경우, 권한 오류 시 대응 |
| 성공 기준 | "완료"의 정의가 모호할 때 | 어떤 상태가 되면 이 프로젝트가 성공인지 |

### 3-2. 진행 방식

1. 위 카테고리 중 해당되는 항목을 판별하여 `AskUserQuestion`으로 질의 (한 번에 최대 4개)
2. 답변에서 추가 질문이 필요하면 이어서 질의
3. **"이 정보면 기획서의 모든 섹션을 채울 수 있는가?"** 를 자문한다
4. 채울 수 없는 섹션이 남아있으면 해당 부분에 대해 추가 질의
5. 모든 섹션을 채울 수 있다고 판단되면 다음 단계로 진행

## 4. 기획서 (`docs/plan.md`) — "누가 · 무엇을 · 왜"

### 4-1. 작성 전 필수 리서치

기획서를 바로 작성하지 않는다. 반드시 아래 리서치를 먼저 수행한다.

1. **웹서치** — 해당 업무 도메인의 모범사례·레퍼런스·주의사항 조사
2. **패키지/라이브러리 조사** — 목적 달성에 필요한 패키지·도구 후보 탐색, 장단점 비교
3. **설치 여부 확인** — 현재 환경에 이미 설치된 패키지 확인 (`pip list`, `npm list`, `conda list` 등)
4. **추천 정리** — 리서치 결과를 기획서에 첨부

### 4-2. 기능 브레이크다운 규칙

기획서의 주요 기능은 반드시 **개발 단위까지 세분화**한다.

- 대기능 → 중기능 → 개발 단위(하나의 커밋 또는 모듈로 구현 가능한 수준)로 분해
- 각 개발 단위에 기술 후보와 벤치마크(성능·안정성·커뮤니티 등)를 기재
- **기술 스택 선택지가 있는 경우** → 옵션별 비교표를 작성하고 `AskUserQuestion`으로 사용자 선택
  - 비교표에 반드시 포함: 장점, 단점, 비용(유료/무료), 라이선스

### 4-3. 역제안 (필수)

기획서 초안 작성 시, 사용자가 고려하지 못했을 가능성이 있는 내용을 **반드시 역제안**한다.

역제안 대상:
- **빠진 기능** — 목적 달성에 필요하지만 사용자가 언급하지 않은 기능
- **리스크** — 기술적 제약, 성능 병목, 보안 취약점 등
- **더 나은 대안** — 사용자 요청보다 효율적이거나 간단한 방법이 있는 경우
- **확장 가능성** — 지금은 불필요하지만 나중에 필요할 가능성이 높은 것
- **범위 과다** — 목적 대비 과도한 요구사항이 있는 경우 축소 제안

역제안은 기획서의 별도 섹션(`## 역제안`)에 기재하고, `AskUserQuestion`으로 수용/거절을 확인한다.

### 4-4. 기획서 템플릿

```markdown
# 기획서 — [프로젝트명]
> 최종 수정일: YYYY-MM-DD

## 개요
- 배경 및 목적 (왜 하는가)
- 기대 효과

## 범위
- 포함 범위 (In-scope)
- 제외 범위 (Out-of-scope)

## 요구사항
- 기능 요구사항 목록 (번호 부여)
- 비기능 요구사항 (성능·보안·운영 등, 해당 시)

## 기능 브레이크다운

| 대기능 | 중기능 | 개발 단위 | 기술 후보 | 벤치마크 |
|--------|--------|----------|----------|---------|
| ... | ... | ... | ... | ... |

## 기술 선택지 (선택이 필요한 항목)

### [항목명]
| 기준 | 옵션 A | 옵션 B | 옵션 C |
|------|--------|--------|--------|
| 설명 | ... | ... | ... |
| 장점 | ... | ... | ... |
| 단점 | ... | ... | ... |
| 비용 | ... | ... | ... |
| 라이선스 | ... | ... | ... |
| **추천** | ✅ 또는 — | | |

## 기술 리서치 결과
- 도메인 조사 요약
- 추천 패키지/도구 (설치 여부: ✅ 설치됨 / ❌ 미설치)

## 입출력 정의
- 입력 형식·출처
- 출력 형식·대상

## 역제안
- (사용자가 고려하지 못했을 내용에 대한 제안 및 근거)

## 제약사항
- 기술·환경·정책 제약

## 미결정
- 아직 결정되지 않은 사항
```

### 4-5. 기획서 검토 (필수)

기획서 초안 완성 후, 사용자에게 보여주기 전에 **검토 에이전트**를 실행한다.

**검토 에이전트 실행 방법:**
`Agent` 도구를 사용하여 아래 관점으로 기획서를 비판적으로 검토하는 서브에이전트를 띄운다.

검토 관점:
1. **완전성** — 누락된 요구사항이나 기능은 없는가
2. **실현 가능성** — 기술적으로 구현 가능한가, 제약사항과 충돌하지 않는가
3. **일관성** — 요구사항·기능·입출력 간 모순은 없는가
4. **범위 적정성** — 목적 대비 과소/과대한 범위는 없는가
5. **리스크** — 간과된 기술적·운영적 리스크는 없는가

검토 결과를 기획서에 반영한 뒤, `AskUserQuestion`으로 사용자 승인을 받는다.
**승인 후** 설계서(`docs/design.md`)·진행상황(`docs/progress.md`) 생성.

## 5. 설계서 (`docs/design.md`) — "어떻게"

> 기획서 승인 후 작성. 기획서에서 브레이크다운된 기능 단위별로 구현 방식을 명확히 정의한다.
> **스스로 개발 가능한 수준**까지 상세화해야 한다.

### 5-1. 설계 원칙

기능 단위마다 아래 항목을 반드시 결정한다:

| 결정 항목 | 설명 |
|----------|------|
| 구현 방식 | 스킬 / 에이전트 / LLM 호출 / 모듈 / 외부 라이브러리 중 선택 |
| 사용 기술 | 패키지명, 버전 |
| 입력 | 데이터 형식, 출처 |
| 출력 | 데이터 형식, 대상 |
| 의존 관계 | 다른 기능·모듈과의 관계 |

- 결정이 어려운 항목 → **스스로 판단하지 않고** `AskUserQuestion`으로 질의
- 기획서 변경 시 설계서도 반드시 함께 검토·수정

### 5-2. 검증 설계 (필수)

- **모든 기능 단위**에 대해 스스로 검증 가능한 테스트 방법을 정의한다
- 입력값·기대 출력·검증 명령어를 명시한다
- **검증 불가능한 설계는 설계 완료로 인정하지 않는다**
- 통과하지 못한 항목은 `progress.md` 미완료 항목에 기재

### 5-3. 설계서 템플릿

```markdown
# 설계서 — [프로젝트명]
> 최종 수정일: YYYY-MM-DD

## 시스템 개요
- 전체 구조 다이어그램 또는 텍스트 구조도
- 주요 컴포넌트 및 역할

## 데이터 흐름
- 입력 데이터 출처·형식
- 출력 데이터 형식·저장 위치
- 흐름: input → process → output

## 기능별 구현 명세

### [기능명]
- **구현 방식**: 스킬 / 에이전트 / LLM / 모듈 / 라이브러리
- **사용 기술**: 패키지명 (버전)
- **입력**: ...
- **출력**: ...
- **의존**: ...
- **핵심 로직**: (의사코드 또는 플로우)

(기능 단위별 반복)

## 예외 & 엣지케이스
- 예상 오류 상황 및 처리 방식

## 검증 체크리스트

### [기능명]
- [ ] 검증 항목 설명
      입력: 예시값
      기대 결과: 예시
      검증 방법: 실행 명령 또는 확인 절차

(기능 단위별 반복)

## 미결정 사항
- 설계 단계에서 결정이 필요한 항목
```

## 6. 진행상황 (`docs/progress.md`)

> 기획서 승인 후 생성.
> **업무가 진행될 때마다 즉시 갱신한다.** 세션 단위가 아니라 작업 단위로 업데이트하여 다음에 해야 할 일을 놓치지 않도록 한다.
> 최근 10회 세션 유지. 오래된 세션은 아카이브하거나 삭제.

```markdown
# 진행상황 — [프로젝트명]
> 최종 수정일: YYYY-MM-DD

## 프로젝트 현재 상태
- 전체 진행률 (체감 기준)
- 현재 블로킹 이슈
- 다음에 할 일 (최우선 1~3개)

## 작업 로그

### YYYY-MM-DD
- [완료] 작업 내용
- [완료] 작업 내용
- [진행중] 작업 내용 — 현재 상태
- [대기] 작업 내용 — 대기 이유
- [결정] 확정된 사항
- [변경] 변경된 사항 — 변경 이유
```

## 9. 변경 관리 규칙

작업 중 내용 변경이 발생하면:

1. **코드 수정 즉시 중단**
2. 변경 내용을 문서에 먼저 반영 (플랜모드)
3. 사용자 승인
4. 승인 후 개발 재개

이 순서를 어기지 않는다. 코드를 먼저 고치고 문서를 나중에 맞추는 것은 금지한다.
