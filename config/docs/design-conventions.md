> 로드 시점: 설계서 작성 시 및 필요 시마다
> 최종 수정일: 2026-03-24

---

## 설계서란 무엇인가

설계서는 **기획서의 "무엇을"에 대해 "어떻게 + 무엇을 통해"를 답하는 산출물**이다.
기획서가 승인된 후 작성하며, 기획서의 **모든 원자 액션**에 대해 구현 방법이 빠짐없이 정의되어야 설계가 완료된다.

설계서가 완성되면 "의사코드만 보고 코드를 작성할 수 있는 상태"가 되어야 한다.
설계서에 없는 내용은 구현하지 않는다 — 먼저 설계서에 추가 후 구현한다.

기획서와 동일하게 설계서도 순서가 있는 프로세스가 아니라 **아래 관심사들이 모두 해소된 상태**를 의미한다.

### 관심사 목록

| 관심사 | 핵심 질문 | 섹션 |
|--------|---------|------|
| 구현 명세 | 각 원자 액션을 어떻게 구현하는가? | A |
| 연결 설계 | 액션들이 어떻게 연결되는가? | B |
| 안전성 | 무엇이 잘못될 수 있고 어떻게 방어하는가? | C |
| 검증 | 올바르게 작동하는지 어떻게 확인하는가? | D |
| 산출물 | 설계서는 어떤 형태인가? | E |
| 유지보수 | 설계서가 바뀌면 어떻게 하는가? | F |

### 관심사 간 의존 관계

```
A (구현 명세) ← 기획서의 원자 액션 목록이 입력
B (연결 설계) ← A의 입출력이 확정되어야 연결 가능
C (안전성)    ← A, B를 기반으로 취약점·예외 식별
D (검증)      ← A, B, C 모두 확정되어야 검증 항목 설계 가능
E (산출물)    ← 모든 관심사의 결과를 설계서로 조립
F (유지보수)  ← 설계서 완성 후 변경 발생 시 적용
```

### 핵심 원칙

- **자체 발생한** "TBD", "추후 결정", "조사 필요"는 설계서에 남길 수 없다 — 조사 후 확정하여 기재
- 단, 기획서에서 `[미확정]`으로 이관된 항목은 설계서 '미결정 사항' 섹션에 `[미확정-기획이관]` 태그로 기재할 수 있으며, 해당 항목이 구현에 필요한 시점 전까지 해소한다
- 결정이 어려운 항목은 `AskUserQuestion`으로 질의하고, 미결정 상태로 두지 않는다
- 기획서의 원자 액션 목록을 그대로 설계서의 작업 단위로 삼는다

## 설계서 완성 조건

아래가 모두 충족되어야 설계가 완료된 것으로 본다.
**설계서 초안 완성 후 `Agent` 도구로 검토 에이전트를 실행하여 아래 항목을 검증한다.**

| # | 검토 항목 | 통과 기준 | 관련 관심사 |
|---|---------|---------|-----------|
| 1 | 원자 액션 커버리지 | 기획서의 모든 원자 액션이 설계에 포함되어 있는가 | A |
| 2 | "어떻게" 완전성 | 모든 액션에 의사코드 수준의 로직이 있는가 | A |
| 3 | "무엇을 통해" 완전성 | 모든 액션에 패키지명·함수명·버전이 명시되어 있는가 | A |
| 4 | 인터페이스 정합성 | 인접 액션 간 입출력 형식이 서로 일치하는가 | B |
| 5 | 데이터 흐름 완성 | 전체 입력→출력 흐름이 끊김 없이 연결되는가 | B |
| 6 | 보안 체크리스트 | 모든 보안 항목이 검토되고 결과가 기록되었는가 | C |
| 7 | 예외·엣지케이스 | 각 원자 액션의 이상 흐름이 정의되어 있는가 | C |
| 8 | 검증 실행 가능성 | 모든 검증 항목이 실제로 실행 가능한 명령어를 포함하는가 | D |
| 9 | 설계 과잉 없음 | 기획서 범위를 벗어난 설계가 없는가 | A, E |
| 10 | 사용자 승인 | `AskUserQuestion`으로 사용자가 설계서를 승인했는가 | — |

검토 통과 후 사용자 승인을 받는다.
**승인 거절 시**: 거절 사유를 확인하고, 해당 사유와 관련된 관심사로 돌아가 부분 재작성한다. 전체 재작성은 사용자가 명시적으로 요구한 경우에만 수행한다.
**승인 후** `engineering.md`를 참조하여 구현을 시작한다.

## A. 구현 명세 — "각 원자 액션을 어떻게 구현하는가?"

설계서의 핵심이다. 기획서의 **모든 원자 액션 하나하나**에 대해 구현 방법을 정의한다.
누락된 원자 액션이 있으면 설계 미완료다.

### A-1. 기술 조사 (구현 명세 작성 전 필수)

모든 원자 액션에 대해 아래 조사를 반드시 수행한다.
조사 없이 구현 방법을 추정하여 기재하지 않는다.
기획서 단계에서 `benchmark` 스킬로 수행한 벤치마크 결과를 기반으로 심화 조사한다.

| 조사 항목 | 내용 | 조사 방법 |
|---------|------|---------|
| 정확한 함수·메서드·명령어 | 실제로 호출할 API 이름, 시그니처 | 공식문서, 레퍼런스 |
| 버전·호환성 | 사용할 버전, 현재 환경 호환 여부 | `pip show`, `npm list` |
| 입출력 형식 상세 | 정확한 타입, 구조, 예시값 | 공식문서, 예제 코드 |
| 알려진 제한사항·버그 | 이 도구의 한계, 주의사항 | GitHub Issues, StackOverflow |
| 더 단순한 대안 | 내장 기능이나 더 간단한 방법이 있는지 | 웹서치 |

**구현 수단이 복수인 경우 (LLM / 스크립트 / 스킬 등):**
- 하나의 원자 액션을 실현할 수 있는 구현 수단이 여러 가지라면, 각 수단의 장단점을 비교표로 정리한다
- `AskUserQuestion`으로 사용자에게 구현 방향을 확인받은 뒤 설계서에 확정 기재한다
- **설계서에 구현 수단이 확정되지 않은 상태로 구현에 진입하지 않는다**

**조사 후 자문:**
- "이 결과만으로 코드를 작성할 수 있는가?" → 예이면 A-2로
- "아직 모르는 것이 있는가?" → 예이면 추가 조사 또는 `AskUserQuestion`
- "구현 수단이 2가지 이상인가?" → 예이면 비교표 작성 후 사용자 승인

### A-2. 구현 명세 항목

각 원자 액션마다 아래 7개 항목을 전부 기재한다:

```
### [원자 액션명] (기획서 트리 참조 ID)

**어떻게 (How):**
구현 방식을 단계별 로직으로 서술한다.
의사코드 또는 순서도 수준으로 작성한다.
"A를 읽어서 B로 변환하고 C에 저장한다" 수준이 아니라
각 단계에서 어떤 처리가 일어나는지 명확히 기술한다.

**무엇을 통해 (Through What):**
- 도구/라이브러리: [패키지명] v[버전]
- 핵심 함수/클래스: [정확한 이름과 시그니처]
- 호출 방식: [실제 코드 수준의 예시]

**입력:**
- 형식: [정확한 타입·구조]
- 출처: [어디서 오는가]
- 필수/선택: [필수 | 선택 (기본값: ...)]
- 예시: [실제 예시값]

**출력:**
- 형식: [정확한 타입·구조]
- 전달 대상: [다음 액션 또는 최종 목적지]
- 예시: [실제 예시값]

**의존 관계:**
- 선행: [이 액션 전에 반드시 완료되어야 하는 액션명]
- 후행: [이 액션 결과를 사용하는 액션명]

**핵심 로직 (의사코드):**
1. 입력 수신 및 유효성 확인
2. [처리 단계 상세]
3. [처리 단계 상세]
4. 결과 반환

**오류 처리:**
| 오류 상황 | 원인 | 처리 방식 | 사용자 안내 |
|---------|------|---------|-----------|
| ... | ... | ... | ... |
```

### A-3. 구현 명세 품질 기준

아래를 만족해야 해당 액션의 설계가 완료된 것으로 간주한다:

- [ ] "무엇을 통해"에 패키지명·함수명이 정확히 명시되어 있는가
- [ ] 입력·출력에 실제 예시값이 있는가
- [ ] 의사코드만으로 코드를 작성하기 충분한가
- [ ] 오류 상황이 최소 1개 이상 정의되어 있는가
- [ ] 선행·후행 의존 관계가 명시되어 있는가

## B. 연결 설계 — "액션들이 어떻게 연결되는가?"

원자 액션은 독립적으로 존재하지 않는다. 이 관심사는 액션 간 데이터가 어떻게 흘러가는지를 정의한다.

### B-1. 인터페이스 계약

인접한 원자 액션 간 데이터를 주고받는 지점마다 인터페이스 계약을 정의한다.
**인터페이스 계약 없이 연결된 액션이 있으면 설계 미완료다.**

```
[액션 A] → (인터페이스) → [액션 B]

인터페이스명: [이름]
전달 데이터 형식: [정확한 타입·구조]
전달 조건: [정상인 경우만 전달 | 오류도 포함하여 전달]
오류 전달 방식: [예외 raise | 오류 코드 반환 | None 반환]
```

### B-2. 데이터 흐름

시스템 전체를 관통하는 데이터의 흐름을 작성한다.
각 화살표에 데이터 형식을 반드시 명시한다.
외부 시스템 연동이 있으면 연동 지점과 프로토콜을 표시한다.

```
[입력 출처: 형식]
       ↓
[원자 액션 A: 변환 내용]
       ↓ (중간 데이터 형식)
[원자 액션 B: 처리 내용]
       ↓ (중간 데이터 형식)
[원자 액션 C: 처리 내용]
       ↓
[출력 대상: 형식]
```

## C. 안전성 — "무엇이 잘못될 수 있고 어떻게 방어하는가?"

정상 흐름뿐 아니라 이상 흐름도 반드시 설계한다.
해당 없는 항목은 "해당 없음"으로 표기한다 (공백 금지).

### C-1. 보안 설계 체크리스트

#### 입력 검증
- [ ] 모든 외부 입력값에 타입·형식·범위 검증이 설계되어 있는가
- [ ] 파일 업로드 시 허용 확장자·크기 제한이 명시되어 있는가
- [ ] SQL/명령어 인젝션 경로에 파라미터 바인딩이 적용되는가

#### 인증·접근 제어
- [ ] 권한이 필요한 기능에 접근 제어가 설계되어 있는가
- [ ] 세션·토큰 관리 방식이 명시되어 있는가 (해당 시)
- [ ] 감사 추적이 필요한 작업이 식별되어 있는가

#### 데이터 보호
- [ ] 민감 데이터의 저장·전송 방식이 명시되어 있는가
- [ ] 비밀키·API키가 환경변수/설정파일로 분리되어 있는가
- [ ] 민감 데이터가 로그에 출력되지 않도록 처리되어 있는가

#### 외부 연동
- [ ] 외부 API 호출 시 타임아웃·재시도 정책이 정의되어 있는가
- [ ] 외부 의존성 장애 시 폴백 또는 사용자 안내가 설계되어 있는가
- [ ] 외부 라이브러리 라이선스가 사용 환경에 적합한가

### C-2. 예외·엣지케이스

각 원자 액션에 대해 아래 상황을 검토하고 처리 방식을 정의한다:

| 상황 유형 | 확인 질문 |
|---------|---------|
| 빈 데이터 | 입력이 없거나 빈 파일일 때 |
| 손상된 데이터 | 형식 불일치, 필수 필드 누락 |
| 권한 오류 | 파일 접근 불가, API 인증 실패 |
| 외부 의존성 장애 | DB 연결 실패, API 타임아웃 |
| 중복 실행 | 같은 작업이 동시 또는 중복으로 실행 |
| 대용량 입력 | 예상보다 많은 데이터 — 성능·메모리 영향 |
| 부분 성공 | 여러 항목 중 일부만 처리 성공 |
| 환경 의존성 누락 | 필요한 패키지·파일·설정이 없는 경우 |

각 상황에 대해 **처리 방식과 사용자 안내**를 설계서에 명시한다.

## D. 검증 — "올바르게 작동하는지 어떻게 확인하는가?"

**검증 불가능한 설계는 설계 완료로 인정하지 않는다.**
이 섹션은 **검증 기준과 기대 결과를 설계**하는 곳이다. 실제 테스트 실행 방식(파일 구조, 실행 순서)은 `engineering.md` §6을 따른다.
모든 원자 액션에 대해 스스로 검증 가능한 방법을 정의한다.

### D-1. 검증 항목 형식

```
### [원자 액션명]

**단위 검증:**
- [ ] 검증 내용: [무엇을 확인하는가]
      입력: [실제 입력값 또는 사전 조건]
      기대 결과: [정상 동작 시 무엇이 나와야 하는가]
      검증 방법: [실행 명령어 또는 확인 절차 — 한 줄로 실행 가능해야 함]

**엣지케이스 검증:**
- [ ] 검증 내용: [경계값 또는 예외 상황]
      입력: [경계값 예시]
      기대 결과: [예외 처리 결과]
      검증 방법: [실행 명령어]
```

**좋은 예시:**
```
- [ ] CSV 파일 정상 파싱
      입력: 헤더 포함 10행 CSV (sample.csv)
      기대 결과: 딕셔너리 리스트 10개 반환
      검증 방법: python -c "from parser import parse; assert len(parse('sample.csv')) == 10"
```

**나쁜 예시 (사용 금지):**
```
- [ ] 파싱이 잘 되는지 확인   ← 구체성 없음
      검증 방법: 실행해서 확인   ← 실행 방법 불명확
```

### D-2. 검증 단계

| 단계 | 설명 | 적용 대상 |
|------|------|---------|
| 단위 검증 | 원자 액션 단독 실행 확인 | 모든 원자 액션 |
| 통합 검증 | 인접 액션 연결 확인 | 인터페이스 계약이 있는 모든 경계 |
| 엣지케이스 검증 | 빈 입력, 최대값, 오류 상황 | 입력 처리가 있는 모든 액션 |
| 완료 검증 | 전체 흐름 end-to-end | 마일스톤 완료 시 |

### D-3. 통과 기준

- 모든 원자 액션의 단위·엣지케이스 검증 항목이 통과되어야 해당 액션 완료
- 통과하지 못한 항목은 `진행내역.md` 미완료 항목에 기재
- 검증 결과(통과 ✅ / 실패 ❌ / 보류 ⏸)를 체크리스트에 업데이트
- 검증 실패 후 코드 수정 시: 실패한 항목과 해당 수정의 영향을 받는 항목만 재검증한다. 인터페이스 계약이 변경된 경우에는 양쪽 액션 통합 검증도 재수행한다

## E. 산출물 — "설계서는 어떤 형태인가?"

### E-1. 문서 규칙

- 모든 문서 상단에 `최종 수정일` 기재, 수정 시마다 갱신
- 기반 기획서의 최종 수정일을 함께 기재 — 기획서 변경 시 설계서도 갱신 필요
- 비어있는 섹션은 `(미작성)` 또는 `(해당 없음)`으로 명시
- 문서 초안은 저장 전에 반드시 `AskUserQuestion`으로 사용자 승인을 받는다
- **설계서는 프로젝트 폴더의 `docs/설계서.md`에 저장한다** — 다른 경로에 저장하지 않는다
- 설계서는 프로젝트당 하나로 유지한다. 마일스톤이 복수인 경우, 원자 액션별 구현 명세에 마일스톤 번호를 표기하고 검증 체크리스트도 마일스톤별로 구분하여 작성한다. 파일을 분리하지 않는다

## F. 유지보수 — "설계서가 바뀌면 어떻게 하는가?"

### F-1. 설계서 업데이트 규칙

구현 중 내용 변경이 발생하면:

1. **코드 수정 즉시 중단**
2. 변경 내용을 설계서에 먼저 반영
3. 기획서에도 영향이 있으면 기획서 동시 수정 (아래 영향도 판단 기준 참조)
   - 설계 과정에서 기획서에 누락된 요구사항·원자 액션을 발견하면, `AskUserQuestion`으로 사용자에게 알리고 기획서 수정·승인 후 설계를 계속한다
4. `AskUserQuestion`으로 사용자 승인
5. 승인 후 개발 재개
6. 변경 이유가 중요하면 `docs/decisions/`에 기록

**코드를 먼저 고치고 문서를 나중에 맞추는 것은 절대 금지.**

| 트리거 | 업데이트 대상 | 연동 문서 | 기획서 영향 |
|--------|------------|---------|-----------|
| 구현 방식 변경 (동일 입출력) | 해당 액션 구현 명세 | `진행내역.md`에 [변경] | 없음 |
| 기술 스택 변경 | 시스템 개요, 해당 액션 | `decisions/`에 변경 이유, `진행내역.md`에 [변경] | 있음 — 기획서 기술 선택지 반영 |
| 인터페이스 변경 | 인터페이스 계약, 데이터 흐름 | 관련 액션 모두 갱신, `진행내역.md`에 [변경] | 입출력 변경 시 있음 |
| 원자 액션 추가/삭제 | 기능 계층 분해, 구현 명세 | `진행내역.md`에 [변경] | 있음 — 기획서 기능 분해 반영 |
| 보안 이슈 발견 | 보안 설계, 해당 액션 오류 처리 | `진행내역.md`에 [결정] | 없음 |
| 검증 실패 | 검증 체크리스트 결과 갱신 | `진행내역.md`에 미완료 기재 | 없음 |
| 오류 처리 추가 | 해당 액션 오류 처리 | `진행내역.md`에 [변경] | 없음 |

업데이트 후 `최종 수정일`을 반드시 갱신한다.
