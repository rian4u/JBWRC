## 1. 구현 전제 조건

코드를 한 줄이라도 작성하기 전에 아래를 확인한다.

**설계서 준수**
- 설계서(`docs/설계서.md`)에 명시된 원자 액션만 구현한다
- 설계서에 없는 기능·로직을 임의로 추가하지 않는다
- 구현 중 설계서와 다른 방식이 필요하면 → 코드 중단 → 설계서 수정·승인 → 재개

**문서 연동 의무**
- 코드·스킬 수정이 발생하면 **수정 직후** `docs/진행내역.md`에 기록한다 (`changelog-conventions.md` 참조)
- 마일스톤 완료 시 `docs/최종산출물.md`를 갱신한다 (`deliverable-conventions.md` 참조)
- 나중에 몰아서 기록하지 않는다 — 변경과 기록은 항상 한 세트다

## 2. 코드 작성 원칙

**가독성 우선**
- 영리한 코드보다 명확한 코드. 6개월 후의 내가 읽어도 이해할 수 있어야 함
- 함수·변수명은 역할을 드러내는 이름으로 (축약 최소화)
- 한 함수는 한 가지 일만

**한글 주석 필수**
- 모든 함수·클래스에 기능 설명과 파라미터 설명을 한글 주석으로 작성한다
- 기능·파라미터 외에도 의도, 주의사항, 배경 등 이해에 도움이 되는 내용은 적극적으로 기재한다
- 주석 없는 코드는 미완성으로 간주한다

**즉시 실행 가능**
- 작성한 코드는 그 자리에서 바로 실행 가능한 완성형으로
- 미완성 코드 제공 시 반드시 명시 (`# TODO:` 또는 `[미구현]`)
- 의존성·실행 환경 조건이 있으면 코드 상단에 주석으로 명시

**오류 처리**
- 예외 상황은 묵인하지 않고 명시적으로 처리
- 사용자에게 의미 있는 오류 메시지 제공
- 데이터 손실 가능성이 있는 작업은 반드시 검증 후 실행

**인증 정보 관리**
- 아이디, 패스워드, API 키 등 인증 정보는 **항상 YAML 파일로 별도 관리**한다
- 코드에 인증 정보를 하드코딩하지 않는다
- YAML 파일은 `.gitignore`에 포함하여 버전관리에서 제외한다

## 3. 언어별 스타일

> 현재 주요 사용 언어 기준. 언어 추가 시 섹션 추가.

**Python**
- 들여쓰기: 4칸
- 타입 힌트 권장 (복잡한 함수에서)
- f-string 사용 (`.format()` 지양)
- 파일 상단에 주요 라이브러리 import 집중

**SQL (Oracle)**
- 예약어 대문자, 컬럼명·테이블명 원본 케이스 유지
- 서브쿼리보다 CTE(`WITH`) 우선 (가독성)
- 파라미터는 `:변수명` 형식, 하드코딩 금지
- 실행 전 영향 범위(건수) 확인 쿼리 먼저

**VBA**
- 프로시저 상단에 목적·입출력 주석
- `On Error GoTo` 로 오류 처리
- 매직 넘버 사용 금지, `Const` 로 상수 정의

## 4. 파일·구조 원칙

**네이밍**
- 파일명: `snake_case` (소문자, 언더스코어)
- 클래스: `PascalCase` / 함수·변수: `snake_case`
- 테스트 파일: `test_` 접두사

**디렉토리 구조**
- 프로젝트 루트에 README 또는 설계서 링크 필수
- 소스코드와 문서는 분리 (`src/` vs `docs/`)
- 설정값은 코드에서 분리 (`.env`, config 파일)

**버전관리**
- 커밋 메시지: `[유형] 내용` 형식 (예: `[fix] SQL 파라미터명 수정`)
- 유형: `feat` / `fix` / `refactor` / `docs` / `test`
- 작업 단위로 커밋, 여러 변경을 한 번에 묶지 않음

## 5. 코드 레벨 설계 원칙

> 시스템 설계는 `design-conventions.md`에서 다룬다. 여기서는 코드 구현 시 적용하는 원칙만 다룬다.

**단순성 우선**
- 필요 이상으로 추상화하지 않음
- 지금 당장 필요한 것만 구현 (YAGNI)
- 복잡한 설계가 필요하다면 먼저 문서화 후 구현

**의존성 관리**
- 외부 라이브러리 도입 시 `docs/decisions/`에 선택 근거 기록
- 핵심 로직에 외부 의존성 최소화

**확장성**
- 나중에 변경될 가능성이 있는 값은 설정으로 분리
- 반복 패턴이 보이면 함수·모듈로 추출

## 6. 테스트 원칙

**자기 검증 필수**
- 테스트 케이스는 설계서 D섹션의 검증 체크리스트를 기반으로 작성한다. 설계서 검증 항목 1개 = 테스트 케이스 1개 이상
- 모든 기능은 스스로 검증 가능한 테스트 케이스를 생성한다
- 테스트를 통과하지 않으면 해당 기능의 개발이 완료된 것으로 간주하지 않는다

**작은 단위 실행**
- 테스트는 기능 단위로 개별 수행한다 — 전체 테스트를 한번에 실행하지 않는다
- 예외: 사용자가 전체 테스트 일괄 실행을 명시적으로 승인한 경우

**테스트 파일 관리**
- 테스트 파일은 `test_` 접두사로 생성
- 해당 기능의 검증이 완료되면 즉시 삭제한다

## 7. 검토 체크리스트

코드 제출·완료 전 확인:
- [ ] 즉시 실행 가능한가
- [ ] 한글 주석이 충분히 작성되었는가
- [ ] 오류 처리가 되어있는가
- [ ] 인증 정보가 YAML로 분리되어 있는가
- [ ] 하드코딩된 값은 없는가
- [ ] 기능별 테스트 케이스가 모두 통과했는가
- [ ] 테스트 파일이 삭제되었는가
- [ ] 변경 내용이 설계서에 반영됐는가
- [ ] 변경 내용이 `docs/진행내역.md`에 기록됐는가
- [ ] 마일스톤 완료 시 `docs/최종산출물.md`가 갱신됐는가
