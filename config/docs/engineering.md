## 1. 코드 작성 원칙

**가독성 우선**
- 영리한 코드보다 명확한 코드. 6개월 후의 내가 읽어도 이해할 수 있어야 함
- 함수·변수명은 역할을 드러내는 이름으로 (축약 최소화)
- 한 함수는 한 가지 일만

**즉시 실행 가능**
- 작성한 코드는 그 자리에서 바로 실행 가능한 완성형으로
- 미완성 코드 제공 시 반드시 명시 (`# TODO:` 또는 `[미구현]`)
- 의존성·실행 환경 조건이 있으면 코드 상단에 주석으로 명시

**오류 처리**
- 예외 상황은 묵인하지 않고 명시적으로 처리
- 사용자에게 의미 있는 오류 메시지 제공
- 데이터 손실 가능성이 있는 작업은 반드시 검증 후 실행

---

## 2. 언어별 스타일

> 현재 주요 사용 언어 기준. 언어 추가 시 섹션 추가.

**Python**
- 들여쓰기: 4칸
- 타입 힌트 권장 (복잡한 함수에서)
- f-string 사용 (`.format()` 지양)
- 파일 상단에 주요 라이브러리 import 집중

**SQL (Oracle)**
- 예약어 대문자, 컬럼명·테이블명 원본 케이스 유지
- 서브쿼리보다 CTE(`WITH`) 우선 (가독성)
- 파라미터는 `:변수명` 형식, 하드코딩 금지
- 실행 전 영향 범위(건수) 확인 쿼리 먼저

**VBA**
- 프로시저 상단에 목적·입출력 주석
- `On Error GoTo` 로 오류 처리
- 매직 넘버 사용 금지, `Const` 로 상수 정의

## 3. 파일·구조 원칙

**네이밍**
- 파일명: `kebab-case` (소문자, 하이픈)
- 클래스: `PascalCase` / 함수·변수: `snake_case`
- 테스트 파일: `test_` 접두사, 작업 완료 후 즉시 삭제

**디렉토리 구조**
- 프로젝트 루트에 README 또는 설계서 링크 필수
- 소스코드와 문서는 분리 (`src/` vs `docs/`)
- 설정값은 코드에서 분리 (`.env`, config 파일)

**버전관리**
- 커밋 메시지: `[유형] 내용` 형식 (예: `[fix] SQL 파라미터명 수정`)
- 유형: `feat` / `fix` / `refactor` / `docs` / `test`
- 작업 단위로 커밋, 여러 변경을 한 번에 묶지 않음

---

## 4. 설계 원칙

**단순성 우선**
- 필요 이상으로 추상화하지 않음
- 지금 당장 필요한 것만 구현 (YAGNI)
- 복잡한 설계가 필요하다면 먼저 문서화 후 구현

**의존성 관리**
- 외부 라이브러리 도입 시 `docs/decisions/`에 선택 근거 기록
- 핵심 로직에 외부 의존성 최소화

**확장성**
- 부서·직무 추가를 고려한 구조 설계
- 하드코딩된 값이 나중에 변경될 가능성이 있으면 설정으로 분리

---

## 5. 검토 체크리스트

코드 제출·완료 전 확인:
- [ ] 즉시 실행 가능한가
- [ ] 오류 처리가 되어있는가
- [ ] 하드코딩된 값은 없는가
- [ ] 테스트 파일이 남아있지 않은가
- [ ] 변경 내용이 설계서에 반영됐는가
